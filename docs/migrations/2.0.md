# Migrating from 1.1.2 to 2.0.0

Version 2.0.0 moves the loader to the current Astro Content Layer and Notion data-source APIs. Follow these steps in order when upgrading from `@chlorinec-pkgs/notion-astro-loader@1.1.2`.

## 1. Update the runtime

Version 2.0.0 supports:

- Node.js `>=22.13.0`
- Astro `>=6 <8`

Update Node.js before installing the package, then upgrade Astro to version 6 or 7. Confirm both versions:

```sh
node --version
pnpm exec astro --version
```

## 2. Replace the package

The package moved from `@chlorinec-pkgs/notion-astro-loader` to `@astro-notion/loader`.

Users on `@chlorinec-pkgs/notion-astro-loader@1.1.2` are not auto-upgraded because the package name changed; the replace step below is required. Users already on `@astro-notion/loader@1.x` receive `2.0.0` as a breaking upgrade when the `latest` dist-tag moves.

```sh
pnpm remove @chlorinec-pkgs/notion-astro-loader
pnpm add @astro-notion/loader@2.0.0 -D
```

Replace imports from the old package name, including schema subpath imports:

```ts
import { notionLoader } from '@astro-notion/loader';
import { notionPageSchema, transformedPropertySchema } from '@astro-notion/loader/schemas';
```

## 3. Select and share a Notion data source

Notion databases are now containers that can hold one or more data sources. Version 2.0.0 queries the Notion SDK's `dataSources` API, so it requires the ID of a specific data source rather than a database ID.

1. Open the data source that contains the pages to load.
2. Share it with the same Notion integration used by the site.
3. Copy its data source ID and replace the old environment variable.

Before:

```sh
NOTION_TOKEN=your-notion-token
NOTION_DATABASE_ID=your-database-id
```

After:

```sh
NOTION_TOKEN=your-notion-token
NOTION_DATASOURCE_ID=your-data-source-id
```

## 4. Update the loader configuration

Replace `database_id` with `data_source_id`. Filters and sorts remain Notion SDK query options, but their properties must exist on the selected data source.

Before (`1.1.2`):

```ts
import { defineCollection } from 'astro:content';
import { notionLoader } from '@chlorinec-pkgs/notion-astro-loader';

const posts = defineCollection({
  loader: notionLoader({
    auth: import.meta.env.NOTION_TOKEN,
    database_id: import.meta.env.NOTION_DATABASE_ID,
    imageSavePath: 'assets/images/notion',
    filter: {
      property: 'Hidden',
      checkbox: { equals: false },
    },
  }),
});

export const collections = { posts };
```

After (`2.0.0`):

```ts
import { defineCollection } from 'astro:content';
import { notionLoader } from '@astro-notion/loader';

const posts = defineCollection({
  loader: notionLoader({
    auth: import.meta.env.NOTION_TOKEN,
    data_source_id: import.meta.env.NOTION_DATASOURCE_ID,
    imageSavePath: 'assets/images/notion',
    publicPath: 'public/notion-assets',
    filter: {
      property: 'Hidden',
      checkbox: { equals: false },
    },
  }),
});

export const collections = { posts };
```

Run `pnpm astro sync --force` after changing the ID. A successful sync verifies that the integration can retrieve the data source and that the query options match its properties.

## 5. Check collection schemas

The loader now implements Astro's dynamic `createSchema()` contract. When a collection omits `schema`, the loader retrieves the selected data source and generates the page-property schema and TypeScript types from its current properties.

If the collection supplies its own `schema`, keep it in `defineCollection()` as before. Update only the package imports and loader ID:

```ts
import { defineCollection } from 'astro:content';
import { z } from 'astro/zod';

import { notionLoader } from '@astro-notion/loader';
import { notionPageSchema, transformedPropertySchema } from '@astro-notion/loader/schemas';

const posts = defineCollection({
  loader: notionLoader({
    auth: import.meta.env.NOTION_TOKEN,
    data_source_id: import.meta.env.NOTION_DATASOURCE_ID,
  }),
  schema: notionPageSchema({
    properties: z.object({
      Name: transformedPropertySchema.title,
    }),
  }),
});

export const collections = { posts };
```

Run `pnpm astro sync --force` and type check the site after changing data-source properties so generated collection types are refreshed.

## 6. Check hosted asset destinations

Version 2.0.0 separates assets by how Astro serves them:

- Notion-hosted images in page content are downloaded below `src/<imageSavePath>` and registered with Astro's image pipeline. `imageSavePath` remains relative to `src` and defaults to `assets/images/notion`.
- Notion-hosted documents, PDFs, video, and audio are downloaded below `publicPath` and rendered with Astro's configured base path. `publicPath` must be inside Astro's `publicDir` and defaults to `publicDir`.
- External asset URLs remain remote.
- Hosted covers, icons, and file properties retain their original URLs unless `cacheImageInData` is enabled. When enabled, hosted images use `imageSavePath` and other hosted files use `publicPath`. The deprecated `experimentalCacheImageInData` alias remains supported for one major and emits a warning when it is effective.
- Use `rootSourceAlias` for the root alias on transformed cover image paths. The deprecated `experimentalRootSourceAlias` alias remains supported for one major. If a canonical option and its legacy alias are both supplied, the canonical option wins and the alias is ignored.

Ensure both configured directories are writable during content sync and that `publicPath` is not outside `publicDir`. If the site has a non-root Astro `base`, verify a rendered public asset URL includes that base.

`fileToImageAsset` now remains a server-only helper because it calls `getImage()` from `astro:assets`. Use it only in build-time or server code, not hydrated client components.

## 7. Verify the upgrade

Run the site's normal checks and a clean content sync:

```sh
rm -rf .astro
pnpm astro sync --force
pnpm astro check
pnpm build
```

Then verify one page with each asset type used by the site. A failing page still fails the whole content sync instead of being cached as current, but the loader now attempts every page and deletion before throwing one aggregated error listing each failed page ID and cause:

- Find the failure in the per-page log output (prefixed with the page ID), fix the page content or rendering input, and rerun the sync. The failed page keeps its prior digest and is retried.

- Collection properties have the expected generated or custom types.
- Page-content images render through Astro's image pipeline.
- Documents and media resolve beneath the configured Astro base path.
- No rendered page depends on an expired Notion-hosted URL that should have been localized.

See the [2.0.0 release notes](../releases/2.0.0.md) for the complete consumer-visible summary.
